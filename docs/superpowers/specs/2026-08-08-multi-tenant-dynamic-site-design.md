# Multi-tenant dynamic Ivy Cleans — design

Approved in conversation 2026-08-08. Turns this repo (the deployed Ivy Cleans
site) into one app that serves a site per city: content generated by Claude
skills through a hidden admin flow, per the client Abdi's brief — "enter the
information up front… it activates a whole bunch of skills… boom, a ready
website."

Companion document: `2026-08-08-dynamic-static-content-list.md` — the
authoritative field-by-field list of what is static, city-swapped, AI-written,
research-derived, or human-entered. That list is the contract; this design is
the machinery around it.

## Goals and non-goals

Goals:

- One repo, one Vercel deployment, serving every city domain.
- Hidden `/admin` (unguessable path, no login) where the operator enters city
  + state + phone, and the Claude pipeline produces a complete draft site.
- Draft → in-place preview → publish lifecycle; nothing AI-written goes live
  unread.
- Minneapolis (the current site) keeps rendering byte-identically as city #1.

Non-goals (explicitly out of scope now, all user-decided):

- AI image generation (slot reserved; images stay as-is).
- Blog changes (`/blog` frozen; blog machine is a separate tool).
- `/book`, `/book-now` (skipped).
- The 24 suburb pages (skipped — a new city's Areas We Serve list renders
  unlinked so nothing 404s).
- Auth (private URL + API spend cap instead), payments, multi-operator roles.

## Architecture

One Next.js app (this repo). Three layers change; everything else stays:

1. **Content layer** — every dynamic slot in the content list moves from
   hardcoded strings in `src/data/*.ts` to a per-city content object. Static
   copy stays exactly where it is today.
2. **Tenant resolution** — middleware maps the request's Host header to a
   city (`miamicleans.com → miami`). Unknown/default host → `minneapolis`.
   `/preview/<city>` renders a draft city regardless of host.
3. **Admin + pipeline** — `/admin-<random>` routes: dashboard, new-city
   wizard, progress, review/publish. Server actions call the Claude API.

### Content model

One JSON document per city, stored in **Vercel Blob** (`content/<city>.json`),
holding every field the content list marks dynamic:

```ts
type CityContent = {
  city: string            // "Miami"
  state: string           // "FL"
  phone: string           // FACT — verbatim from the form, never via AI
  status: 'draft' | 'live'
  domain?: string         // set at publish
  research: {
    suburbs: { name: string; slug: string }[]   // slugs stored, never derived
    zips: string[]
    landmarks: string[]
    mapEmbedUrl: string | null
  }
  sections: { [slotId: string]: string | string[] }
  // slotId enumerates every AI + CITY slot from the content list, e.g.
  // 'home.hero.intro', 'front.services.dusting.text', 'deep.whatIs'
}
```

- **CITY-class slots** are not stored as copies of the template text; the
  template keeps the canonical copy with `{city}` / `{cityState}` tokens and
  interpolation fills them. Only AI- and RESEARCH-class content is stored.
  This keeps static copy in exactly one place (the repo) so a copy fix never
  requires touching city documents.
- **Minneapolis** is seeded once from the current `src/data/*.ts` values and
  becomes `content/minneapolis.json` with `status: 'live'`. A rendering
  equivalence check (see Testing) proves the refactor changed nothing.
- Blob writes go through one storage module (`src/lib/content-store.ts`) so a
  later move to Postgres is contained.

### Tenant resolution and URLs

- `middleware.ts` resolves Host → city key from a small domain index
  (`content/_domains.json`, updated at publish). Result is passed via request
  header to layouts/pages.
- City-in-URL routes (confirmed by user): the deep-cleaning and move-out
  pages register per-city slugs — `/deep-cleaning-miami`,
  `/miami-move-out-cleaning-services` — generated from the city key. The
  Minneapolis slugs remain unchanged.
- `/preview/<city>` prefixes the whole route tree for drafts (implemented as
  an optional route segment / rewrite), gated by nothing but obscurity, same
  as `/admin`.
- Rendering uses ISR: pages read the city JSON with caching; publishing and
  saving drafts trigger `revalidate` so updates appear without a redeploy.

**As built (Plan 2b):** the `/preview/<city>` sketch above was not built as a
separate prefix; the internal `/<cityKey>/…` paths that already exist under
`app/(sites)/[city]/…` ARE the preview, no extra mechanism needed:

- The rewrite lives in `src/proxy.ts`, not `src/middleware.ts` — Next 16
  renamed the file convention from `middleware` to `proxy`
  (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`),
  same mechanism, current name. The rewrite decision itself is the pure,
  unit-tested `resolveRewrite()` in `src/content/resolve-rewrite.ts`; `proxy.ts`
  is a thin adapter around it.
- Draft cities render on demand at their own `/<cityKey>/…` path (Next's
  `dynamicParams = true` on `[city]`) with every internal link built via a
  `cityHref(c, path)` helper: for a `status: 'draft'` city, `cityHref` prefixes
  the path with `/<cityKey>` so the whole preview is walkable page-to-page; for
  a `status: 'live'` city it returns the bare public path unchanged, so
  Minneapolis's HTML — and any other published city's — stays on its clean
  public URLs.
- Preview passthrough is a default-host-only behavior. `resolveRewrite()`'s
  logic: a **mapped** production host (an entry in `_domains.json`'s `hosts`)
  always rewrites to that host's city, full stop — a mapped host never checks
  whether the first path segment looks like a city key, so a live tenant's own
  domain can never accidentally serve a different city's preview under a
  colliding path segment. Only on the **default** host does an unmapped first
  path segment that matches a known city key (from `content/_cities.json`)
  pass through untouched — that's what makes `localhost:3100/testville/home`
  and (in production) `default-domain/testville/home` work as a preview link,
  by design, while `minneapolis.example.com/testville/home` would not skip the
  rewrite (it isn't the default host).
- `content/_domains.json` (`{ default, hosts: Record<host, cityKey> }`) and
  `content/_cities.json` (a flat array of every known city key, draft and
  live) are the publish contract: Plan 3's admin flow writes a new
  `content/<key>.json`, appends the key to `_cities.json`, and — only at
  actual publish, once a domain is attached — adds the host mapping to
  `_domains.json`. The store's `revalidateCity(key)` invalidator is what the
  admin's publish/save-draft actions call so updates appear without a
  redeploy.

### Claude pipeline (ported from the proven generator)

Model: `claude-opus-5` via the Anthropic SDK, streaming, structured outputs
(Zod schemas per skill) — the same pattern the microsite generator used in the
successful 2026-08-08 Miami dry run. Server-side env: `ANTHROPIC_API_KEY`
(with a Console spend cap), `BLOB_READ_WRITE_TOKEN`.

Skills, run in order, each resumable and individually re-runnable:

1. **Research** — input: city, state. Uses Claude's web-search server tool.
   Output (schema-validated): suburbs (with stored slugs in the live site's
   varied patterns), real ZIP codes, real landmarks, map embed URL, plus a
   keyword/entity brief for "cleaning services {city}". Facts are
   web-grounded; the phone is never part of any prompt.
2. **Writers** — one call per page group (front hero+services, home
   sections, deep-cleaning, move-out), consuming the research brief. Output:
   the AI-class slots only. CITY-class swaps are pure string interpolation in
   code — the model cannot alter static copy.
3. *(reserved)* **Images** — future skill; no-op now.

Per-slot regenerate = re-run one writer with the same research brief.

### Admin UX (approved screens)

1. **Dashboard** — every city + status (LIVE / DRAFT), links to preview,
   entry to the wizard.
2. **New City** — city, state, phone, optional notes. Client-side validation
   (state code, phone shape) before any paid call.
3. **Progress** — live checklist as skills complete (research → each writer).
4. **Review** — open full preview (`/preview/<city>`); edit suburb list;
   per-section regenerate; domain field + Publish. Publish is disabled until
   the preview has been opened at least once this visit.

Publish v1: sets `status: 'live'`, writes the domain index, revalidates.
Attaching the domain to the Vercel project is a documented one-time manual
step in the Vercel dashboard (automating via Vercel API is a later nicety).

### Error handling

- Model call failures: retry once, then surface on the progress screen with a
  per-skill retry button; partial results persist (resume, don't restart).
- A draft can never break a live site: live rendering reads only
  `status: 'live'` documents; malformed/missing draft JSON renders a plain
  "draft not ready" page under `/preview` only.
- Blob unavailability on a live domain: pages fall back to the last ISR-cached
  render.

## Testing

- **Equivalence gate (the critical one):** before/after HTML snapshots of
  every Minneapolis route must match (modulo whitespace) once content flows
  through the new layer. This proves the refactor is invisible.
- Schema tests: every slotId in the content list exists in the writer
  schemas and is consumed by exactly one component (no orphan slots, no
  unfilled slots).
- Pipeline tests with a stubbed model client (same pattern as the generator).
- One real end-to-end generation (Miami) as the acceptance test, reviewed in
  `/preview/miami`.

## Findings from Plan 1's final review (inputs to Plans 2–3)

Recorded 2026-08-08 after the content-layer rollout step passed all gates.

1. **Tenancy mechanism (drives Plan 2's design):** data files evaluate at
   module scope, so per-request tenancy cannot be a `currentCity` swap —
   data exports become functions of a city (or AsyncLocalStorage), with
   ~41 consumers updated. Client components (Header, InnerHeader, Reviews,
   WorkCarousel) need the city via props/context.
   **RESOLVED Plan 2b:** implemented as `app/(sites)/[city]/…` route
   segments + an async content store (`getCity(key)`), not
   AsyncLocalStorage — every page/layout receives `params: Promise<{ city
   }>`, awaits it, and threads `CityContent` down via props (matching the
   ~41-consumer estimate). Client components receive the resolved city (or
   just the bits they need, e.g. `cityKey`) as props from their server
   parents.
2. **ZIPs/landmarks representation:** `research.zips`/`research.landmarks`
   are seeded empty and unread; the rendered facts live in the
   `home.zipParagraph`/`home.landmarksParagraph` prose slots. Plan 3's
   research schema must pick one canonical form (recommend: keep the
   structured arrays as research output, have the writer compose the prose
   slots from them, keep both in the document).
   **RESOLVED Plan 3**, exactly as recommended: `ResearchSchema` returns
   structured `zips`/`landmarks` arrays, they are stored on the document as
   `research.zips`/`research.landmarks`, and the `home` stage composes
   `home.zipParagraph`/`home.landmarksParagraph` from those arrays (the
   prompt embeds the arrays and forbids any zip or landmark outside them).
   Both representations live in `content/<key>.json`.
3. **Contact-page details:** the contact address is a third live-site
   variant kept literal (see content-list doc); `mapEmbedUrl ?? ""` renders
   an empty-src iframe — Plan 2 should conditionally omit the map instead.
   **RESOLVED Plan 2b:** `CityContent.maps.{front,home,contact}` are each
   `string | null`; `ServiceArea`/`MapEmbed`/`ContactMap` render nothing
   when the value is null instead of an empty-src iframe.
   `CityContent.contactAddress?: string` was added, with `contactData`
   reading `c.contactAddress ?? c.address` — Minneapolis's contact page
   keeps its distinct "Suite 208" variant, byte-identical.
4. **Loader hardening for Blob (Plan 2):** replace the unchecked
   `raw as CityContent` cast with runtime validation, and move `s()`/`sl()`
   throws out of module-eval so one bad city document can't poison all
   tenants for the process lifetime.
   **RESOLVED Plan 2b:** `src/content/validate.ts` hand-rolls
   `validateCityContent(raw: unknown): CityContent`, accumulating every
   missing/mistyped field into one thrown error rather than the first; the
   store runs every document through it before returning, so a bad
   `content/<key>.json` 404s only that city, not the process. Includes a
   key↔name guard: the document's own `city` name is cross-checked against
   the registry/file key it was loaded under, so a copy-paste city-key
   mismatch fails validation instead of silently serving under the wrong
   key.
5. **Full state name token (found in Plan 2a Task 4):** the front page's SEO
   title contains the literal word "Minnesota"; `CityContent` stores only the
   two-letter code, so Plan 2b/3 must add a `stateName` field (admin form or
   a code→name map) and a `{stateName}` token before any non-Minnesota city
   ships. Marked with a PLAN-2B TRAP comment at the literal.
   **RESOLVED Plan 2b:** `CityContent.stateName: string` added
   (`"Minnesota"` for Minneapolis, `"Testonia"` for the Testville fixture);
   `{stateName}` is a first-class interpolate.ts token; the front metadata
   literal now reads `"…{city} {stateName} - Ivy Cleans"` and the PLAN-2B
   TRAP comment is deleted.
6. **Maps — THREE embeds, three treatments (Plan 2a Tasks 5 + final review):**
   contact page is wired to `research.mapEmbedUrl`; `src/components/home/MapEmbed.tsx`
   is a hardcoded Minneapolis-coordinates URL; `src/components/ServiceArea.tsx`
   (front page) is a hardcoded business-search URL with the street number. None
   contain a city-name literal, so greps can't see them. Plan 2b sources all
   three per city (extend CityContent map fields).
   **RESOLVED Plan 2b:** all three embeds now live in `CityContent.maps`
   (`front`/`home`/`contact`), each seeded byte-exactly from its former
   hardcoded literal for Minneapolis; components take a `mapSrc: string |
   null` prop and render nothing when null (see finding 3).
6b. **book.ts is NOT city-free (Plan 2a final review):** the round-9 booking
   pages hardcode the phone in three exports (`bookLeadIn` — as "(612) 424-0391"
   display format, `bookCallNow`, `comingSoon`), rendered by BookSection and
   ComingSoonPanel. Plan 2b must parameterize these, including a display-format
   phone variant (or second field) since CityContent.phone is "612-424-0391".
   **RESOLVED Plan 2b:** `src/data/book.ts` is now a `bookData(c:
   CityContent)` builder threaded through the book pages/components (same
   R3 props pattern as round 2a); the display-format phone comes from the
   new `CityContent.phoneDisplay` field. Pinned by a new, separate snapshot
   test (`tests/book-data.test.ts`, hash `058bf52a…`) — the Plan-1
   data-equivalence pin was left untouched, since it has no `book` entry.
6c. **Grep gates must be case-insensitive:** Task 7's `grep "Minneapolis"` missed
   two lowercase `-minneapolis` hrefs (since fixed). Future sweeps use `-i`.
   **RESOLVED Plan 2b:** every Minneapolis sweep in Plan 2b's gates used
   `grep -in` throughout Tasks 3–6; no further lowercase misses surfaced.
7. **Gate limitations (fine for Plan 1, know them):** the HTML crawler
   strips all scripts (blind to flight-only/JSON-LD content) and only
   crawls links reachable from `/`; the seed extractor is now
   self-referential and must never be re-run.
8. **Preview-escape leftovers (frozen blog scope):** `src/data/posts.ts` (3
   hrefs) and `src/data/blog.ts` (8 hrefs) hold bare public-path hrefs
   (e.g. `/how-to-clean-bathroom-walls`) that were never routed through
   `cityHref()`, and `src/components/blog/Pagination.tsx` links to
   `/blog/2`, `/blog/3`, … which are dead (no such routes exist). A viewer
   walking a draft-city preview can click a blog card or a pagination link
   and land back on the default-host public path, escaping the
   `/<cityKey>` preview context. Acceptable for now — `/blog` is frozen,
   out of scope per this spec's non-goals, and the blog tool that will
   eventually own these files doesn't exist yet — but any future blog work
   must route these hrefs through `cityHref()` too.
9. **`usePathname` client components must strip the `/<cityKey>` prefix.**
   Any client component that path-matches against `usePathname()` (active-nav
   highlighting, breadcrumbs, etc.) will mismatch on a draft-city preview
   because the live pathname carries the `/<cityKey>` prefix that the
   component's own hrefs (built via `cityHref`, which omits the prefix for
   live cities) don't expect. `src/components/inner/InnerHeader.tsx`
   established the fix — a small `stripCity()` helper strips a leading
   `/<cityKey>` segment from both the raw pathname and each candidate href
   before comparing — and this pattern is required for any future
   path-matching client component, not just InnerHeader.

## As built (Plan 3) — admin + pipeline

Recorded 2026-08-08 after Plan 3 Task 6. Everything below describes code that
exists and is exercised by `pnpm test` plus `scripts/admin-e2e.mjs`; where it
differs from the design sketch above, this section is the truth.

### The admin route and its four screens

`/admin-x7kq92mpfw4rt8vz` — the unguessable segment IS the folder name under
`src/app/`, mirrored as a value in `src/app/admin-x7kq92mpfw4rt8vz/base.ts`
(renaming the admin means editing the folder and that one line). It sits
OUTSIDE `app/(sites)/[city]`, so it can never contribute a byte to a customer
page, and `src/content/resolve-rewrite.ts` passes any first segment starting
with `admin-` through untouched — but only on the default host (see the
limitations below). All four screens are `force-dynamic`; every one of them
reflects on-disk state the operator is actively changing.

1. **Dashboard** (`page.tsx`) — one table merging two sources:
   `content/_cities.json` (finalized cities, the document's own `status` field
   deciding LIVE vs DRAFT) and `content/_drafts/*.json` (sidecars, i.e.
   in-flight cities). Statuses: LIVE, DRAFT, GENERATING (`n/4 stages`),
   NEEDS FINALIZE, ERROR. Each row links to the preview `/<key>` and to
   Review / Resume / Finish as appropriate.
2. **New City** (`new/page.tsx`) — a plain server-rendered
   `<form action={createDraftAction}>`: city, 2-letter state, phone in any
   format, optional address, optional notes ("the only field the AI reads").
   Errors come back as `?error=…` and re-render above the form. The phone is
   stripped to digits in `createDraftFromFields`, and `deriveFacts` is the
   single validator for the 10-digit and state-code rules.
3. **Generate** (`generate/[key]/page.tsx` + `stage-runner.tsx`) — a client
   runner walks the four stages in order, ONE server-action call per stage,
   then calls `finalize`. Per-stage calls (not one long request) keep every
   request short enough for a serverless duration cap, make each failure
   individually retryable, and let a reload resume from `draft.done`.
4. **Review** (`review/[key]/page.tsx`) — "Open preview ↗" to `/<key>`; the
   suburb editor (name+slug rows, slugs normalized server-side); per-stage
   Regenerate; and the Publish box (optional domain, `window.confirm`, then a
   success panel that names the manual Vercel domain step).

### Pipeline stages, and the two-call research design

`src/pipeline/stages.ts` — `STAGES = ['research','front','home','deep']`,
each `(client, key) => Promise<void>`: load sidecar → return early if the
stage is already in `done` → call the model → persist outputs → append to
`done`. `regenerateStage` deletes exactly the stage's own outputs
(`STAGE_SLOTS`) first; regenerating `research` also clears `front`/`home`/
`deep`, because those consumed it.

**Research is deliberately two model calls** (`src/pipeline/model.ts`):

1. `client.research(prompt, key)` — a streaming call carrying the
   `web_search_20260209` server tool and NO `output_config`; it returns free
   findings text.
2. `client.generate({ schema: ResearchSchema, … })` — a second call whose only
   job is to structure those findings, carrying `output_config.format`
   (`zodOutputFormat`) and NO tools.

Server tools and structured outputs are kept in separate requests by design.
Both calls opt into `betas: ['server-side-fallback-2026-07-01']` with
`fallbacks: 'default'`, and both check `stop_reason === 'refusal'` and throw a
readable error, which the stage runner shows with a Retry button.

The three writer stages consume the research object: `front` →
`services.heroParagraphs`, `services.serviceIntro`, `services.cards.*`;
`home` → the ZIP and landmarks prose composed from the arrays (finding 2);
`deep` → `deep.whatIs`. Ten section slots in total (`REQUIRED_SLOTS`), and the
union of `STAGE_SLOTS` equals that list exactly — pinned by a test, so no slot
can become unregenerable or unwritable.

FACTS ARE NEVER MODEL OUTPUT. `deriveFacts()` (`src/pipeline/facts.ts`) turns
the form's city/state/10 digits into `phone` (`612-424-0391`), `phoneDisplay`
(`(612) 424-0391`), `phoneHref` (`tel:6124240391`) and `stateName` from a
50-state + DC map. No phone number, address or state name is ever in a prompt.

### Draft sidecar contract (`content/_drafts/<key>.json`)

```
DraftDoc = { facts, research?, sections: Record<slot, string|string[]>,
             done: string[], createdAt }
```

- It is NOT a `CityContent` and would fail `validateCityContent` — `sections`
  is a partial map until every stage has run.
- `key = citySlug(facts.city)`; `createDraft` refuses if a sidecar OR a
  published document already exists for that key.
- **`finalizeDraft(key)`** assembles a full `CityContent` from the sidecar
  (status/domain excepted — see below), runs `validateCityContent`, writes
  `content/<key>.json`, idempotently appends the key to `content/_cities.json`
  and calls `revalidateCity(key)`. Missing research or slots throw an error
  naming every one of them. Defaults for a new city: `hasSuburbPages: false`,
  all three `maps` null, `research.mapEmbedUrl` null, and — when the operator
  left the address blank — the honest placeholder `"<City> — address pending"`
  (validation requires a non-empty address, and a street address must never
  come from a model).
- **LIVE-STATUS CARRY-FORWARD:** finalize rebuilds the whole document, so it
  reads the previous `content/<key>.json` first (`existingPublication`) and
  carries `status` and `domain` forward. Without that, re-finalizing after a
  regenerate would demote a live city back to `draft` and drop its domain
  while `_domains.json` still routed the host to it — the site would 404 for
  real visitors on a real domain. A finalize refreshes COPY; it never
  publishes and never un-publishes. A city's first finalize starts as `draft`.
- The sidecar SURVIVES finalize (so copy can still be regenerated) and is
  deleted by publish. Its presence is exactly "this city can still be
  regenerated", which is what the Review screen keys off.

### Publish contract, as implemented

`publishCity(key, domain?)`:

1. read + validate `content/<key>.json`, set `status: 'live'`;
2. if a domain was given: lowercase it, strip any port, store it as
   `doc.domain`, and write it into `content/_domains.json` `hosts` — REMOVING
   any other host that previously pointed at this key, so a re-publish under a
   new domain cannot leave the old host silently serving the same city;
3. `revalidateCity(key)`; 4. delete the draft sidecar.

The calling server action then does `revalidatePath('/', 'layout')` (blunt on
purpose: a city is reachable both at its public paths via the host rewrite and
at its `/<cityKey>` preview prefix, so there is no single path to invalidate).
Publishing does NOT attach the domain to the Vercel project — that stays the
documented manual step, and the success panel says so.

### STUB_MODEL and the browser E2E

`makeClient()` returns `StubModelClient` when `process.env.STUB_MODEL === '1'`,
reading canned Stubville copy from `tests/fixtures/stub-pipeline.json` through
the real zod schemas (so a stale fixture fails loudly instead of drifting).
Every unit test and the browser E2E run this way; NO test, script or gate ever
makes a live API call. The only live-API step in the whole plan is the
user-gated Miami run.

`scripts/admin-e2e.mjs` (verification tooling, run by hand, not in CI) drives
the real UI with Playwright: dashboard → New City → four stages → finalize →
review (suburb editor, preview in a second tab: `/stubville` 200, generated
copy, `tel:` href, `/stubville`-prefixed nav, unlinked suburbs) → Publish with
no domain → dashboard shows LIVE, then deletes the generated city and restores
`_cities.json`/`_domains.json` byte-for-byte.

**It requires `STUB_MODEL=1 pnpm dev --port 3100`, not `pnpm start`.** Stub
mode itself works fine under `next start` — the flag is read at call time, and
a prod-server run was observed generating, finalizing and publishing Stubville
correctly, failing ONLY the five preview checks. The reason is that
`src/content/resolve-rewrite.ts`
statically imports `content/_cities.json`, so the proxy's city list is INLINED
AT BUILD TIME. A city created after the build is not in it, `/stubville` is
not recognized as a preview path, and the request is rewritten to
`/minneapolis/stubville` → 404. In production this is not a bug (a real
publish is followed by a redeploy, which is when the domain gets attached
anyway); it just means an end-to-end test of a from-scratch city needs a
server that recompiles from disk.

### Known limitations (Plan 3)

1. **The stage runner's in-flight guard is per-tab.** `StageRunner` holds a
   `busy` ref so one tab cannot start a stage twice, but two tabs open on the
   same `/generate/<key>` will each start the pipeline and can run the same
   stage concurrently — a duplicated paid model call, and a last-write-wins
   race on the sidecar. There is no server-side lock; a stage lease in the
   sidecar (or a mutex around `runStage`) is the fix, deferred as future work.
2. **Preview-escape links in blog content** (finding 8 above, still true):
   `src/data/posts.ts`, `src/data/blog.ts` and `blog/Pagination.tsx` emit bare
   public-path hrefs that never go through `cityHref()`. Clicking a blog card
   inside a draft-city preview leaves the `/<cityKey>` context and lands on
   the default tenant. The E2E reports these rather than failing on them.
3. **Admin exposure on unmapped hosts.** The `admin-` passthrough sits inside
   the default-host branch, so hosts listed in `_domains.hosts` (customer
   domains) deny the admin by construction — but every OTHER host reaches it:
   the raw `*.vercel.app` URL, any unrecognized Host header, and a customer
   domain attached in Vercel but not yet registered by publish. The
   unguessable path is the ONLY access control. That is a deliberate v1
   trade-off; real auth is the fix if it stops being enough.
4. **The admin writes to the local filesystem, and the proxy's city list is a
   build-time constant.** Both are fine locally and NOT yet fine on Vercel: a
   serverless filesystem is ephemeral, so a city generated on a deployment
   would not survive, and even within one instance its `/<cityKey>` preview
   would 404 until a redeploy re-inlines `content/_cities.json` into the proxy
   bundle (the same mechanism that forces the E2E into dev mode). Wiring
   `BLOB_READ_WRITE_TOKEN` — and giving the proxy a runtime source for the
   city list — is what turns the admin into a true hosted tool. Until then the
   supported workflow is: generate locally, review, commit the content files,
   redeploy.
5. **Still out of scope**, as planned: images (the slot is reserved, no
   generation), the blog (frozen, shared across tenants), the booking copy,
   per-suburb pages (`hasSuburbPages: false` for every generated city, so the
   area list renders unlinked), Resend contact routing, Vercel API automation,
   and any admin authentication.

## As built (Plan 4) — live activity feed

Recorded 2026-08-11 after Plan 4 Task 4. Adds a per-stage activity feed to the
Generate screen; the flow, the stage engine and the public site are unchanged.

**Progress log.** `src/pipeline/progress.ts` — framework-free
(`node:fs/promises` + `node:path` only, no `next/*` import) so the same module
can be called from a server action and reasoned about independent of Next.
Each in-flight draft gets a sidecar at `content/_drafts/<key>.progress.json`:
a flat JSON array of `ProgressEvent = { at, stage, kind, label }`
(`kind: 'start' | 'search' | 'reading' | 'found' | 'done' | 'error'`), capped
at `PROGRESS_CAP = 500` entries (oldest dropped first). Concurrent appends for
the same key are serialized through a module-level per-key promise chain, so
a research stage's synchronous `onEvent` callback can never race a
read-modify-write cycle and drop an event. `stages.ts` appends a `start`
before each stage's model call and a `done` (with a human-readable digest)
after; the research stage additionally forwards every `ResearchEvent` its
streaming search call emits (`search`/`reading`) and a `found` digest once
structuring finishes. The file is deleted by `publishCity()` — same lifecycle
as the draft sidecar it sits beside, so a published city leaves no progress
log behind, and `scripts/admin-e2e.mjs`'s cleanup `rm`s it (`force: true`) if
a run aborts before publish.

**Reading it back.** `getProgressLogic(key)` (`src/pipeline/admin-logic.ts`)
reads the log plus the draft's `done` array and, once research has completed,
the researched suburb names/ZIPs/landmarks as plain strings (not the
`{name, slug}` objects the draft stores them as). Wrapped as the server action
`getProgressAction(key)` returning `ProgressSnapshot`.

**Polling is display-only.** `StageRunner` (`generate/[key]/stage-runner.tsx`)
keeps its existing engine completely untouched — the `busy` ref, the
sequential `runStageAction` loop, retry, and auto-finalize are still the sole
driver of generation. A separate `useEffect` polls `getProgressAction` every
1.2s into a `snapshot` state var purely for rendering; stopped once
`finalizePhase === 'done'`, since nothing more will be appended after that.
If the poll effect were deleted entirely, generation would proceed exactly as
before — only the feed would go blank.

**Skill framing.** `src/app/admin-x7kq92mpfw4rt8vz/skills-meta.ts` — a
client-safe, zero-import `SKILL_META` map (icon/name/tagline per `StageId`)
that reframes the four pipeline stages as named "skills" on screen. Each
`<li>` is a skill card: icon badge + name + status glyph, tagline, then an
activity area sourced from `snapshot.events.filter(e => e.stage === stage.id)`
— while running, the last 3 non-error events as mono lines (newest pulsing via
the `admin-pulse` CSS keyframe in `admin.css`); once done, the last summary
line (`found` wins over `done` when both exist, since research's `done` event
is just "Research complete" — the useful digest is its preceding `found`).
When `stage.id === 'research'` and the snapshot carries researched data, a
wrap of chips renders every suburb name plus ZIP/landmark count pills,
independent of whether research is still the running stage.

**Stub fixture.** `tests/fixtures/stub-pipeline.json` → `events.research`: three
canned `ResearchEvent`s (`search`, `search`, `reading`) that `StubModelClient`
replays through the same `onEvent` callback the real streaming client uses, so
`STUB_MODEL=1` runs (all unit tests, `scripts/admin-e2e.mjs`) exercise the
identical append path a live run does.

**Accepted limitation.** The mapping from Anthropic's actual research-stream
events to `ResearchEvent`/`ProgressEvent` is verified by TypeScript types and
the stub fixture, not by a live streamed response — `STUB_MODEL=1` is what
every automated gate (`pnpm test`, `scripts/admin-e2e.mjs`) uses, and no gate
here makes a real API call. Confirming the live mapping (event ordering,
label wording under real search-tool traffic) is deferred to the next live
generation run, the same user-gated step Plan 3 used for Miami.

## As built (Plan 5) — suburb ("Areas We Serve") pages

Recorded 2026-08-14 after Plan 5's three tasks. Every city now gets a real
page per researched suburb (e.g. `/cleaning-service-savage-mn` for
Minneapolis, `/house-cleaning-coconut-grove` under Miami's preview prefix) —
pure token substitution from a fixed template, zero AI cost — and the
"Areas We Serve" links (`ServiceArea.tsx` on `/`, `Locations.tsx` on `/home`)
go live for any city with suburb pages enabled.

**Third slug class.** `src/app/(sites)/[city]/(inner)/[serviceSlug]/page.tsx`'s
dynamic segment now resolves THREE legal value classes, all computed from the
city document, still with no catch-all: (1) `/deep-cleaning-<citySlug>`, (2)
`/<citySlug>-move-out-cleaning-services`, (3) any slug in
`c.research.suburbs[].slug` (exact match — never derived, since the live
site's own suburb URL patterns vary: `house-cleaning-*`,
`cleaning-services-*`, `cleaning-service-*`, `*-cleaning-services` all appear
across the fixtures). `resolveService` tries deep, then move, then the
suburbs array; anything else still 404s. `generateStaticParams` only appends
suburb slugs `when c.hasSuburbPages` — a city without the flag gets no real
static routes for them, though `dynamicParams = true` still lets a draft
preview resolve an un-generated suburb slug on demand (same as deep/move).

**Token model.** `src/data/suburb.ts`'s `suburbData(c, suburb)` holds the
template copy byte-verbatim from the live Savage reference
(`docs/superpowers/reference/ivycleans-live/suburb-savage-content-dump.txt`),
parameterized on exactly two tokens: `{suburb}` (the suburb's display name)
and `{city}`/`{citySlug}`/`{state}` (the metro `CityContent`, via the
existing `t()`/`cityHref()` helpers). Unlike `deepCleaningData`/
`moveOutData`, this builder takes a second argument — the page repeats once
per suburb, not once per city, and `SuburbRef` (`{ name, slug }`) is never
stored on `CityContent` itself; callers pass one entry from
`c.research.suburbs`. Six new server components
(`src/components/suburb/*`) render the six template sections; none are
`"use client"` except where they delegate to the pre-existing
`WorkCarouselGallery` (see below).

**`hasSuburbPages` semantics.** `finalizeDraft` (`src/content/drafts.ts`)
stamps every newly finalized draft `hasSuburbPages: true` — a draft city's
suburb pages go live at the same moment the rest of its content does, no
separate switch. The operator can still edit the suburb list (name/slug) on
the review screen before publish; pages follow whatever slugs end up stored
on the document, immediately, since `generateStaticParams`/`resolveService`
both read `c.research.suburbs` directly rather than a point-in-time copy.
`content/miami.json`, `content/houston.json`, `content/minnesota.json` and
`content/testville.json` were hand-flipped `false → true` to bring the three
existing generated cities in line with new drafts; `content/minneapolis.json`
was already `true`.

**AI-free.** Suburb pages involve no model calls at all — the template is
pure token substitution over data the research stage already produced
(`c.research.suburbs`), so lighting up 24 (Minneapolis) or a handful (draft
cities) of new pages per city costs nothing beyond the one-time research
call that already ran.

**WorkInAction carousel adjudication.** Task 2 shipped the "Our Work In
Action" gallery as a static wrapping row (all 5 images at once), reasoning
that suburb components should stay server-only since hundreds of these pages
will exist per city. Task 3's fidelity pass measured this against live and
found it a real, unfixable-by-CSS defect: the live gallery section is a flat
395px tall at every width (only 1/2/3 of the 5 images ever visible at once,
governed by the same carousel `src/components/home/WorkCarousel.tsx` already
implements for `/home`), while the static row is up to 3.6x taller at narrow
widths. Resolution: `WorkCarousel.tsx`'s carousel body (everything except
`/home`'s own differently-styled heading) was extracted as a new named export,
`WorkCarouselGallery`, and `src/components/suburb/WorkInAction.tsx` renders
its own (suburb-specific) heading followed by `<WorkCarouselGallery
workImages={...} />` — the cheapest faithful option available, since no
static layout can show only 1–3 of 5 images without paging logic (i.e.
without building a carousel anyway), and the carousel already existed,
already matched the live container/settings exactly, and was already proven
at `/home`. This adds one small "use client" leaf per suburb page (the same
leaf `/home` already ships); the page and every other section stay server
components. `/home`'s own `WorkCarousel` default export is unchanged.

**Fidelity finding: the kit's widget-spacing floor.** Beyond the carousel,
the task-3 pass found that several suburb headings and text-editor wrappers
under-counted their live trailing margin because they reproduced only the
page-specific per-id CSS override (from `post-664.css`) and missed a
page-wide default in the KIT stylesheet, `post-6.css`:
`.elementor-widget:not(:last-child){margin-block-end:2rem}` — a 2rem floor
under every Elementor widget that has a following sibling, on top of (not
replacing) that widget's own per-id override. Confirmed empirically (live vs
local probes at six widths) that adjacent-WIDGET margins resolve to the MAX
of the two sides' totals, while a widget followed by a plain (non-widget)
row/container ADDS instead. Fixed per-widget across
`SuburbHero.tsx`/`HouseCleaning.tsx`/`Benefits.tsx`/`OtherServices.tsx`/
`Closing.tsx`, each citing the specific mechanism that applies to it. Also
fixed: `OtherServices.tsx`'s image quirk (element `320da712`'s
`height:329px` is unconditional at every width in the live CSS, not just
below `xl` as task-2 assumed) and `WorkInAction.tsx`'s heading (h3's kit
default is `font-weight:600`, not 700, and it has no page-specific color
override so it inherits the kit's `#374151`, not black) — and
`SuburbHero.tsx`'s H1: the live markup is a literal newline (not a `<br>`),
which HTML whitespace-collapses to a space, so the heading naturally
reflows; a forced `<br>` reproduced two lines unconditionally, which is
wrong at exactly 768px width for Savage (and will be wrong at other widths
for longer/shorter suburb names, since this template repeats per-suburb).

## Deployment runbook (Vercel)

One-time, for the existing Vercel project:

1. **Deploy the app.** Push/deploy as normal; the build prerenders only LIVE
   cities (`generateStaticParams` → `listLiveCityKeys`), and draft cities
   render on demand at `/<cityKey>` because `dynamicParams` stays true.
2. **Environment variables** (Project → Settings → Environment Variables):
   - `ANTHROPIC_API_KEY` — required for real generation. Set a SPEND CAP on
     the key in the Anthropic Console before using it; a runaway retry loop in
     the admin is otherwise unbounded. Never commit it (`.env*` is gitignored;
     see `.env.local.example`).
   - `STUB_MODEL` — do NOT set in production. Locally, `STUB_MODEL=1` makes
     every pipeline call return the Stubville fixture instead of calling the API.
   - `BLOB_READ_WRITE_TOKEN` — LATER, not yet needed. The store already has a
     Blob branch (`getCity`/`listLiveCityKeys` read from Vercel Blob when this
     is set); until then, content lives in the repo's `content/` directory,
     which means a generated city is only durable once it is committed and
     redeployed. Switching to Blob is what makes publish survive a redeploy
     without a commit.
3. **Publishing a city** — in the admin: generate → review → Publish with the
   domain. That writes `content/<key>.json`, `_cities.json` and
   `_domains.json`. Then, MANUALLY: add the domain to the Vercel project
   (Project → Domains) and point its DNS at Vercel. Until the app is
   Blob-backed, also commit the three content files and redeploy — the
   redeploy is also what re-inlines the city list into the proxy bundle.
4. **Verify** the new host serves the city (not the Minneapolis default), and
   that `/<cityKey>` still previews.

**Task 7 — the first real (paid) generation, Miami on the live API — is
pending explicit user approval and has NOT been run.** Everything above was
validated with the stub client only.
